# AI Usage Disclosure

This project was built with an AI coding assistant, **Claude Code** (Anthropic, Claude Opus 5.5),
working directly in the repository: creating files, running commands, executing tests, starting the
servers and driving a real browser. The prompts are in
[prompt-history/prompts.md](../prompt-history/prompts.md). AI assistance applies to the whole
repository and is disclosed here and in the prompt history rather than per commit.

## How the work was split

| Activity | Who |
|---|---|
| Problem definition, requirements, acceptance criteria | Developer (the brief in P1) |
| Architecture, physical model, detection rules, data design | AI proposed and implemented; documented in [DESIGN_DECISIONS.md](DESIGN_DECISIONS.md) |
| Backend, data generator, simulation, detection, tests | AI-written |
| Frontend foundation (API client, types, UI kit, layout) | AI-written |
| Frontend pages | AI sub-agents (three in parallel), integrated and reviewed by the main AI session |
| Documentation | AI-written from the implemented code and measured results |
| Running, verifying, reviewing, deciding what to submit | Developer, with AI-run verification evidence below |

## Where AI accelerated the work

* **Scaffolding and boilerplate** — models, schemas, CRUD routers, the API client and typed
  interfaces were generated in minutes instead of hours.
* **Domain modelling** — turning the brief's equations into a consistent hydraulic model (pump curve
  intersected with a system curve, tank integration, leaks, blockages, valve resistance) and
  calibrating pumps so the synthetic plant is stable.
* **Parallel frontend build** — ten pages built by three sub-agents at once against a shared,
  pre-built foundation.
* **Verification at scale** — a 102-check API smoke test, browser checks of every page, and a
  regeneration fingerprint check were scripted and run rather than done by hand.

## Where the work relied heavily on AI

Being explicit: **essentially all source code and documentation in this repository was generated by
the AI assistant** from the brief. Areas where the reliance was greatest, and which therefore deserve
the closest human understanding:

1. **The hydraulic model** (`backend/app/simulation/`) — the closed-form operating point, the leak
   and blockage formulation, and the starvation approximation.
2. **The detection rules and thresholds** (`backend/app/anomaly_detection/`) — especially the
   three-way flow/tank-level reconciliation that separates leaks from meter faults.
3. **The evaluation method** (`backend/app/services/evaluation_service.py`) — the 6-hour window
   confusion matrix that makes true negatives countable.
4. **Fault-injection design** (`backend/app/generation/faults.py`) — including the deliberate
   below-threshold "detection-limit" faults.

### Problems found during verification (and fixed)

AI-generated code had real defects that only surfaced through testing. Each was diagnosed and fixed:

| Defect | How it was found | Fix |
|---|---|---|
| CRUD create endpoints treated the request body as a query parameter (string annotations hid the Pydantic types from FastAPI) | Workflow test failed with 422 | Removed `from __future__ import annotations` from the router factory module |
| Duplicate-name check counted names reused across facilities (142 false duplicates) | Reported by a frontend sub-agent reading live data | Uniqueness checked per facility |
| A pump starved by an upstream blockage was reported as `PUMP_DEGRADATION` | Scenario sweep across all facilities | Head-deficit rule suppressed while the suction tank is at its low-level alarm; regression test added |
| Every chart silently lost its axes, grid, tooltips and legends (Recharts needs them as direct children) | Visual browser inspection | Chart helpers called as functions; verified by counting rendered axes |
| Initial detection scored a perfect 1.0 — unrealistic and uninformative | Reviewing the first evaluation | Added near/below-threshold faults so the metrics show real detection limits (recall 0.85) |

## Judgement calls to be able to defend

These were decided during the build and are worth being able to explain in a walkthrough
(see [WALKTHROUGH.md](WALKTHROUGH.md) for suggested answers):

* Why the model is quasi-steady and not a network solver.
* Why the detector knows operator setpoints but not fault parameters.
* Why missing readings are stored as `NULL` rows (keeps exactly 100,000 rows).
* Why evaluation is window-based and what that does to the true-negative count.
* Why some faults were made deliberately undetectable.

## Developer's own review

How I worked with the assistant, and what I checked myself.

**Defined the problem and the definition of done.** I wrote the requirements brief: the stack, the
entities and identifiers, the data volumes and seed, the physical equations, the detection rules, the
eight scenarios, the five negative cases and the documentation set. I also set the working rules —
build in phases, run and fix after each phase, document every assumption, and never fabricate metrics.
Everything the assistant built was measured against that brief.

**Steered the build across sessions.** The work ran over interrupted sessions. Each time I had the
assistant resume from the files already on disk rather than start again, so earlier work was kept,
checked and extended.

**Required proof that it works, not just code.** Before treating the build as finished, I asked for
the application to be verified end to end from a clean restart and for exact start-up commands. I
then started the backend and frontend myself with those commands and used the application locally.

**Owned version control and publication.** I committed and pushed the project to GitHub myself, then
reviewed the repository against the submission guidelines and asked what was still missing before
submitting the URL.

**Made the submission decisions.**
- I chose not to publish raw chat transcripts and to record the prompts as a condensed engineering log
  that states it is condensed.
- I asked for my single commit to be reorganised into reviewable commits, on the condition that no
  timestamps were backdated and my original commit was kept on a backup branch. I perform the
  force-push to GitHub myself after reviewing the result.

**What I rely on as evidence.** I do not ask reviewers to trust the generated code. Every result I
quote can be re-run with the commands in the README: 43 passing tests, the 102-check end-to-end smoke
test, the evaluation metrics including the three intentionally missed faults, the 24 scenario runs and
the five negative scenarios.

**What I would question or do differently with more time.**
- The detection thresholds were tuned against the same noise model that generated the data, so the
  high precision says more about the synthetic generator than about a real plant. I would validate
  the rules on real or independently generated data before trusting them.
- The hydraulic model only supports series pump lines. A small network solver would be needed for
  branched or looped piping.
- I would commit incrementally while building instead of organising the history at the end.
